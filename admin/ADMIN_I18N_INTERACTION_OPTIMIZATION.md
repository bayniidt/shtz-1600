# Admin 中英文内容编辑交互优化方案

> 文档状态：Phase 1 已落地，Phase 2（内容管理核心模块）已落地，Cases / Careers 接入中  
> 适用范围：`admin/` 后台的内容管理、客户案例、招聘城市与招聘职位  
> 本期语言：中文（主语言）+ English（目标语言）  
> 不包含：Web 前台语言切换、机器翻译、翻译供应商接入

## 1. 背景与目标

当前后台已经可以把中文内容保存在文档主字段中，并把英文内容保存在 `translations.en`。功能层面能够存储双语，但操作仍以“切换整张表单后编辑”为主，用户很难判断：

- 当前看到的是已录入英文，还是系统从中文回退出来的内容；
- 切换语言前的修改是否仍然保留；
- 点击“保存”保存的是当前语言、当前板块，还是全部内容；
- 哪些字段需要翻译，哪些链接、ID、图片、日期等字段两种语言共用；
- 一个模块还有多少英文内容没有完成。

本方案的核心目标是把“语言切换表单”改造成“中英文对照翻译工作台”，让用户始终看得到中文原文、明确知道正在编辑英文，并能一次保存所有未提交修改。

## 2. 当前流程审查

### 2.1 审查范围

本次在桌面端实际走查了以下流程：

| 步骤 | 操作 | 当前健康度 | 观察结果 |
|---|---|---|---|
| 1 | 从内容管理表格选择模块 | 良好 | Table + Dialog 入口统一，模块定位清楚 |
| 2 | 打开“站点与导航”编辑弹框 | 一般 | 操作按钮固定可见，但字段量大，语言入口弱 |
| 3 | 中文切换为 English | 较差 | 英文缺失时直接展示中文回退值，用户无法区分真实译文和回退内容 |
| 4 | 编辑首页 6 个板块 | 较差 | 每个 Tab 独立维护语言状态，需要反复切换；保存范围不明确 |
| 5 | 切换语言后关闭或保存 | 高风险 | 其他语言草稿可能仍在内存中，但未保存提示会消失；关闭 Dialog 后草稿丢失 |

### 2.2 已确认的高优先级问题

#### P0：切换语言会隐藏未保存状态

当前 `ContentEditor` 在切换语言时会把当前值暂存到 `drafts[locale]`，随后把 `dirty` 重置为 `false`。这会带来两个问题：

1. 用户修改中文后切到英文，页面不再提示中文仍未保存；
2. 此时关闭 Dialog 不会触发可靠的未保存确认，组件销毁后内存草稿丢失。

同样，用户在两种语言都做了修改后点击“保存”，当前实现只保存当前语言，另一种语言的内存草稿不会一起提交。

#### P0：英文回退值与真实译文不可区分

`getLocalizedValues()` 会把中文主字段和英文覆盖层递归合并。英文缺失时，输入框直接显示中文值。视觉上没有“来自中文回退”的标识，用户可能把中文内容误认为已有英文翻译，也可能直接保存，从而把中文复制成正式英文译文。

#### P1：所有字段都被当作可翻译字段

当前语言切换作用于整张表单。链接、图片、业务 ID、邮箱、电话、日期、坐标、开关、分类值等共享字段也会进入 `translations.en`。这增加了重复编辑和数据不一致风险。

#### P1：数组译文按下标合并

导航、数据指标、团队、发展历程、案例区块等数组通过下标对齐中文与英文。中文侧插入、删除或排序后，已有英文内容可能对应到错误条目。

#### P1：没有翻译进度

内容管理表格只有“可编辑”状态，用户无法看到英文完成度，也不能筛选“未翻译”“部分完成”“已完成”。

#### P2：语言切换入口弱，保存文案含义模糊

“编辑语言”位于弹框工具栏右侧，和还原、取消、保存混排。“保存”没有说明保存范围，首页还叠加了板块 Tab，用户需要同时理解“模块、板块、语言”三层上下文。

## 3. 设计原则

1. 中文是主语言和结构来源；英文是对应译文，不单独维护结构。
2. 默认展示中英文对照，不依赖用户记住上一屏中文内容。
3. 共享字段只编辑一次，不进入英文翻译覆盖层。
4. 任何语言或板块存在草稿时，整个 Dialog 都必须保持“未保存”状态。
5. 保存按钮必须明确说明范围，并一次保存当前 Dialog 内所有草稿。
6. 英文缺失、中文回退和正式译文必须有不同视觉状态。
7. 数组条目必须通过稳定标识关联，不能长期依赖数组下标。

## 4. 推荐交互方案

### 4.1 默认使用“双语对照”模式

移除当前作为主操作的“中文 / English”整表切换，改为三个查看模式：

- `中英对照`：默认模式，左侧中文只读，右侧英文编辑；
- `仅中文`：中文可编辑，适合先维护主内容；
- `仅英文`：英文可编辑，适合集中翻译和校对。

模式切换只改变布局，不改变草稿，也不清除未保存状态。

桌面端推荐布局：

```text
┌ 编辑首页内容 · Hero 区 ────────────────────────────────────────────────┐
│ [中英对照] [仅中文] [仅英文]     英文进度 8/12     [预览] [取消] [保存全部] │
├──────────────────────────────────────────────────────────────────────┤
│ 共享设置：链接 / 图片 / ID / 开关                              [展开] │
├──────────────────────────┬───────────────────────────────────────────┤
│ 中文原文                  │ English                                  │
│ 主标题                    │ Main title                    [缺少翻译] │
│ 全球智能营销科技服务商     │ [输入英文标题________________________]    │
│                          │ [复制中文] [清空译文]                      │
├──────────────────────────┼───────────────────────────────────────────┤
│ 首屏简介                  │ Hero description                          │
│ Facebook、Google……       │ [输入英文简介________________________]    │
└──────────────────────────┴───────────────────────────────────────────┘
│ 本模块有 3 处未保存修改                     [放弃修改] [保存全部修改] │
└──────────────────────────────────────────────────────────────────────┘
```

### 4.2 区分三类字段

为 `FieldSpec` 增加字段级本地化元数据：

```ts
type LocalizationMode = "translated" | "shared" | "source-only";

interface BaseField {
  // 默认根据 kind 推断，也允许显式覆盖
  localization?: LocalizationMode;
}
```

建议默认规则：

| 字段类型 | 默认模式 | 示例 |
|---|---|---|
| 文本、长文本 | `translated` | 标题、描述、按钮文案、地址 |
| 链接中的 `label` | `translated` | “查看案例” |
| URL、图片、数字、开关、Select 值 | `shared` | `/cases`、Logo、年份、是否置顶 |
| 业务 ID、slug、数组稳定键 | `source-only` | 案例 ID、城市 ID、行业 key |

共享字段集中放在“共享设置”区域，只显示和保存一份。英文侧不再重复展示或提交这些字段。

### 4.3 英文字段状态

每个可翻译字段显示明确状态：

| 状态 | 显示 | 说明 |
|---|---|---|
| 未翻译 | 灰色 `未翻译` | `translations.en` 中没有该字段 |
| 使用中文回退 | 黄色 `前台将显示中文` | 前台当前会回退中文，但输入框不能伪装成正式英文 |
| 已翻译 | 绿色 `已翻译` | 英文覆盖层中存在非空值 |
| 中文已更新 | 橙色 `原文已变更` | 中文在英文完成后发生修改，需要复核英文 |
| 有未保存修改 | 蓝点或 `未保存` | 当前字段存在本地草稿 |

英文输入框缺失时保持为空，中文内容显示在左侧参考栏；不要把中文回退值直接写进英文输入框。若需要快速复用，提供字段级“复制中文”操作，并明确复制后仍标记为“待翻译”。

### 4.4 保存与退出

Dialog 顶部保留轻量操作，底部增加固定操作栏。顶部和底部操作使用相同状态来源。

按钮文案：

- 主按钮：`保存全部修改（3）`；
- 没有修改时：`已保存`，按钮禁用；
- 次按钮：`取消`；
- 危险操作：`放弃全部修改`，仅有草稿时出现；
- 单语言模式可以显示辅助说明：`将同时保存中文和 English 草稿`。

关闭按钮、取消按钮、点击遮罩和 Esc 都必须统一走未保存确认：

```text
仍有 3 处修改未保存
中文 1 处 · English 2 处

[继续编辑] [放弃并关闭]
```

保存失败时保留全部草稿，并在顶部显示失败原因；成功后清空所有语言的草稿和未保存计数。

### 4.5 首页多板块

首页的 6 个 Tab 保留，但每个 Tab 显示状态：

- `Hero 区 · 2`：2 处未保存；
- `媒体资源区 · 英文 60%`：英文未完成；
- `Flow AI 区 ✓`：双语完整且已保存。

Dialog 顶部显示总进度，底部“保存全部修改”一次提交所有已编辑板块。切换 Tab 不改变语言查看模式，避免每个板块重复选择 English。

### 4.6 数组和嵌套内容

数组结构由中文主语言管理：

- 新增、删除、排序只在中文或“共享设置”中进行；
- 英文侧只翻译条目中的可翻译字段；
- 英文模式不显示删除、排序按钮，避免破坏两种语言的对应关系；
- 每个条目显示中文标题，帮助用户确认正在翻译哪一项；
- 条目折叠标题优先使用中文主标题，并附英文状态。

短期可以在英文侧锁定结构，并沿用现有下标映射。正式方案应为数组条目补充稳定的内部键，例如 `_translationKey`，中文调整顺序后仍能正确关联英文译文。

### 4.7 内容管理列表

内容管理表格调整为更有决策价值的字段：

| 内容模块 | 中文状态 | English 状态 | 最近更新 | 操作 |
|---|---|---|---|---|
| 首页内容 | 完整 | 68% · 缺 14 项 | 2026-09-21 | 编辑翻译 |
| 关于我们 | 完整 | 未开始 | 2026-09-20 | 编辑翻译 |

筛选器调整为：

- 模块；
- English 状态：未开始、部分完成、已完成、需复核；
- 关键词。

删除当前价值较低的“可编辑”状态筛选和 API 地址列；接口信息属于开发信息，不应占据内容运营的主要工作区。

## 5. 各模块交互要求

### 5.1 站点与导航

- 公司名称、地址、导航文案、页脚文案、SEO 文案支持双语对照；
- Logo、ICP、邮箱、电话、链接地址为共享字段；
- 导航和页脚结构仅中文侧可增删排序；
- SEO 区显示中英文字符数和搜索结果预览。

### 5.2 首页、About、招聘文案

- 保持现有板块或分组结构；
- 所有标题、描述、按钮文案双语成对显示；
- 媒体名称、Logo、颜色、坐标、年份等按字段语义设为共享；
- 支持“复制本板块中文到英文”，但必须二次确认且不得覆盖已有英文。

### 5.3 客户案例

- 案例 ID、年份、行业枚举、封面图、图片、链接、置顶状态为共享字段；
- 标题、客户名、地区、简介、标签、数据说明、正文区块为翻译字段；
- 列表增加 English 完成度，支持筛选“英文未完成”；
- 预览按钮允许选择“中文预览 / English 预览”。

### 5.4 招聘城市与职位

- 城市 ID、职位 ID、发布日期、热招/急招、城市归属、申请链接为共享字段；
- 城市名称、简介、职位名称、部门、职责、要求和加分项为翻译字段；
- 城市关联职位只读表格不随语言重复；
- 职位列表显示 English 状态，支持批量定位缺失译文。

## 6. 状态与数据规则

### 6.1 草稿状态

建议把当前单个 `dirty: boolean` 改为统一草稿仓库：

```ts
interface EditorDraftState {
  zh?: Record<string, unknown>;
  en?: Record<string, unknown>;
  shared?: Record<string, unknown>;
  dirtyPaths: Set<string>;
}
```

Dialog 的未保存状态由 `dirtyPaths.size > 0` 决定，不能在切换语言、Tab 或查看模式时重置。

### 6.2 翻译完整度

完整度只统计标记为 `translated` 的可见字段：

```text
英文完成度 = 非空英文译文字段数 / 应翻译字段总数
```

数组按实际条目展开统计。共享字段、可选且中文为空的字段不进入分母。

第一阶段可在前端根据返回数据实时计算；如果列表查询性能不足，再由 Server 返回 `translationStatus` 摘要。

### 6.3 中文变更后的复核

理想方案为每个模块保存 `translationsMeta.en.sourceUpdatedAt` 或内容摘要。当中文在英文译文之后更新时，英文状态变为“需复核”。如果本期不增加服务端元数据，先不展示“需复核”，避免产生不可靠状态。

## 7. 可访问性要求

- 中英状态不能只依赖颜色，同时显示文字或图标；
- 模式切换、保存、复制中文和清空译文都要有明确的可访问名称；
- 键盘 Tab 顺序按“中文参考 → 英文输入 → 字段操作”推进；
- 固定操作栏不能遮挡最后一个字段，内容区需保留底部安全间距；
- 校验失败后聚焦第一个错误字段，并在模块 Tab 上显示错误数量；
- Dialog 关闭后焦点返回触发编辑的按钮；
- 中文只读参考使用可选择文本，便于复制，但不能被误认为禁用输入框。

## 8. 开发拆分建议

### Phase 1：先消除数据丢失和状态歧义（P0）

1. 草稿状态提升为 Dialog 级，切换语言和 Tab 不清除 dirty；
2. 所有关闭入口增加统一未保存确认；
3. 保存按钮改为“保存当前语言”或直接实现“保存全部修改”，禁止继续使用含义不清的“保存”；
4. 英文缺失时输入框为空，并显示中文回退提示；
5. 内容管理列表增加英文完成度。

### Phase 2：中英文对照工作台（推荐主版本）

1. 增加 `localization` 字段元数据；
2. 实现 `BilingualField`、`BilingualGroupList` 和共享字段区域；
3. 默认双栏对照，保留仅中文 / 仅英文模式；
4. 首页 Tab 增加草稿数和英文进度；
5. Cases、城市、职位接入同一交互模型。

### Phase 3：结构稳定与校对能力

1. 嵌套数组增加稳定翻译键，替代下标关联；
2. 增加中文更新后“需复核”状态；
3. 增加按缺失字段筛选、逐项跳转和模块级预览；
4. 评估批量导入导出或机器翻译，但不作为本方案前置条件。

## 10. 验收标准

### 核心流程

- 用户打开任一编辑 Dialog，默认能同时看到中文原文与英文输入；
- 英文缺失时不会在英文输入框中伪装成已有译文；
- 用户修改中文后切换英文、切换首页 Tab，再切回时内容保持；
- 任一语言或板块存在修改时，关闭 Dialog 必须提示未保存内容；
- “保存全部修改”成功后，两种语言和所有已编辑板块都持久化；
- 保存失败后所有草稿仍在，错误信息可见；
- 共享字段只编辑一次，不重复写入 `translations.en`；
- 内容列表可以看到并筛选 English 完成度。

### 数组内容

- 英文侧不能新增、删除或排序中文主结构；
- 中文新增数组条目后，英文侧立即出现对应的待翻译条目；
- 中文排序后，已有英文译文仍对应原条目；
- 删除中文条目前提示该条目的英文译文也会删除。

### 自动化测试

- 覆盖中文、英文和共享字段的 payload 生成；
- 覆盖切换模式、语言和 Tab 后草稿不丢失；
- 覆盖关闭确认、保存全部、部分失败与重试；
- 覆盖英文缺失、部分完成、已完成状态计算；
- 覆盖数组新增、删除、排序后的译文关联；
- 保持 Admin 覆盖率四项均不低于 80%。

## 11. 成功指标

上线后可用以下指标验证优化是否有效：

- 完成一个模块中英文录入所需的语言切换次数降低 80% 以上；
- 因关闭 Dialog 或切换 Tab 导致的草稿丢失为 0；
- 用户能在 5 秒内判断某模块英文是否完成；
- 英文内容中误保存中文回退值的情况显著下降；
- 内容运营无需理解 `translations.en` 数据结构即可完成双语维护。

## 12. 推荐结论

优先实施 Phase 1，先解决草稿丢失和英文回退不可辨识两个高风险问题；随后以“双语对照 + 共享字段 + 保存全部”为核心完成 Phase 2。不要继续在现有整表语言切换模式上增加提示语，因为它无法解决用户需要来回记忆中文、保存范围不清和数组结构错位这些根本问题。
